## Answers to pre-build questions (2026-11-02)

1. **Wake-up timing**
   - a. A tap _before_ wake time counts as on time (`done_full`).
   - b. **Late cutoff is 7:00 AM.** Tap between wake time + window (5:20) and 7:00 → `done_late`. After 7:00 the "I'm up" button disappears and the wake-up quest is **missed** for that day. _(Rishi changed this from the suggested noon.)_ The cutoff is a setting (`wake_late_cutoff`, default 07:00).
2. **Shields/repair and streak count**
   - a. A shielded or repaired day **keeps** the streak but does **not** increase it.
   - b. Shielded/repaired days do **not** count toward the 7 consecutive active days that earn a shield (the 7-day counter pauses on them, it doesn't reset).
3. **Long absences**: shields cover missed days in order. The Recovery quest appears on the return day and repairs a day **only if exactly one unprotected missed day** stands between today and the streak; otherwise it gives Easy XP and a fresh start (no repair). "Max one repair per 7 days" = **rolling 7 days**.
4. **Bonuses**
   - a. Daily Clear = flat +20, no streak bonus, does not count toward the 300 soft-cap threshold.
   - b. Stat XP for an event = the **same final (post-bonus, post-cap, rounded) amount** credited to the player.
5. **Editing a habit mid-day**: today's instance takes the new target/difficulty only if still `pending`; if already completed today, it keeps its snapshot and the change applies from tomorrow.
6. **GitHub**: Rishi has a GitHub account. `gh` CLI is installed (v2.97.0). Claude creates the private repo **`ascend`** with `gh` after Rishi runs `gh auth login`. Branch `main`, one commit + push per task.
7. **Hosting**: **Vercel**, connected to the GitHub repo (auto-deploy on push). Set up at the end of Phase 1.
8. **Sign-in (Phase 7)**: Supabase **email magic link + Google** sign-in. No passwords.
9. **Developer tools**: exist only in `npm run dev`; fully stripped from production builds and the APK.
10. **Day 1 / late start**: if onboarding is after 6 PM and Rishi picks "start tomorrow", Day 1 = tomorrow and tonight is neutral. "Start today" → Day 1 = today, still neutral.

It happens **quietly**: no "level down" message, animation or notification — the number simply corrects. No level is ever lowered for any other reason.
- **Core changes apply from tomorrow** (task 2.1 — Claude's call, change it if you disagree): turning a habit's core flag on or off, or adding a new habit, never changes whether _today_ counts as active. A habit added today appears today and can be done, but isn't core until tomorrow. Reason: adding a core habit at 10 PM shouldn't break today's streak, and removing core from a missed habit shouldn't fake an active day. Other edits (title, target, difficulty, wording) update today's quest while it's still pending (answer 5).
- **Pause / archive / delete apply from today** (task 2.1): today's quest disappears if still pending; if already done today it stays done. Restoring brings today's quest back. A restored core habit comes back non-core if 3 core habits already exist.
- **Permanent delete** (task 2.1): needs an explicit confirmation; the habit is hidden for good (soft-deleted, so past days keep their history) and can't be restored in the app.
- **XP engine details** (task 2.2): (1) a same-day un-tick cancels that award's whole revision before any bonus or cap is applied, so a correction can never leave soft-cap leftovers and the result is identical in any sync order; (2) rounding happens once per stat per day (not per event), so minimum + top-up always equals the full award (a Normal minimum is 12.5); (3) the soft cap counts XP after the streak bonus; (4) Daily Clear is derived from the day, not stored as an XP event, so it updates automatically when a late action re-evaluates a day.
- **Steps and sleep entries are totals** (task 2.3 — Claude's call): for `steps` and `sleep_hours`, a manual entry is the day's total, not an addition; the latest manual entry wins, otherwise the latest Health Connect reading (manual always wins, SPEC 6.4). Entering 7 h then correcting to 7.5 h gives 7.5 h. Minutes and counts still add up from every source.
- **Completion rules** (task 2.3): progress only goes up during a day (Full → Minimum needs an un-tick first; a lower steps/sleep correction doesn't downgrade the status). Un-ticking a numeric quest also resets its progress to zero (a compensating entry). The wake-up quest can only be completed with "I'm up" (on time ≤ wake time + window, including early taps; late until the cutoff; after the cutoff it can't be checked in). Tapping after the day has closed says "That day is closed"; real actions arriving late (widget, notification, sync, Health Connect) are accepted for the day they happened.
- **Day record** (task 2.4): `active`, `neutral` and `daily_clear` are recomputed in the same transaction as every change to that day. A day's `timezone` is the device timezone when the day was first recorded. Low energy hides non-core quests that aren't done yet; done quests stay visible.
- **Streak details** (task 2.5 — Claude's call, change any you disagree with): (1) an unprotected miss counts as broken straight away — the return day starts at streak 0 (no streak bonus) and completing the Recovery quest restores the streak and its bonus; this way XP is only ever raised later, never taken back; (2) neutral days between the miss and the return day don't block a repair; (3) the rolling 7 days are counted between the days the Recovery quests were completed; (4) today never counts as a miss until it closes, so no shield is used early; (5) a miss when the streak is already 0 uses no shield; (6) everything is recomputed from all days in order, so a late action that changes an old day gives the same result as on time.
- **Day rollover** (task 2.6 — Claude's call): runs at startup (before the first screen), whenever the app returns to the foreground, and on a timer at the next day-start hour. It closes every unclosed past day from the start day on, filling days the app was never opened (their quests become `missed`, no XP change). Days are never back-filled with a habit created after them. Today's quests are created at the same time. Streak fields on `days` are recomputed whenever a day's result changes, a day closes, or a Recovery quest is ticked/un-ticked.
- **When a Recovery quest appears** (task 2.6): on today, if the last non-neutral closed day was missed and not covered by a shield or repair (never on Day 1). It repairs that day only when the streak engine allows (exactly one unprotected miss, rolling 7 days); otherwise it's Easy XP and a fresh start. One per day (id `recovery:<day>`, so two devices never make two). It's a Full-only check quest; the text rotates through 5 small 10-minute tasks in `src/data/recovery.ts`. Unfinished, it closes as "not done" with no penalty.
- **Derived state** (task 2.7 — Claude's call): level, stat levels, total XP, rank and streaks are never stored; they are computed from `xp_events`, `days` and `quest_instances` (`engine/progressState.ts`) and kept in a Zustand store (`core/state/progress.ts`) that reloads after every action. The only stored derived values are the `days` fields. **Rank** = the highest rank reached at the end of any day, so it never goes down (a same-day correction of today can still quietly undo a rank-up from a mistaken tap, like levels).
- **Consistency check** (task 2.7): runs at every startup (before the rollover) and from "Rebuild progress": re-evaluates every day from its quests, recomputes streaks and writes only what was wrong. It reads every quest once, which is fast even for years of data; if it ever gets slow, task 10.6 can switch to a checksum. `meta.derived_version` forces a full rebuild if the rules behind the stored fields change.

## Phase 7

- **Server schema** (task 7.1 — Claude's call): one generic table, `sync_records` — a row per local record (`tbl`, `id`) with the record as JSON — instead of copying all 20 local tables into Postgres. The server only stores the latest version of each record per user; the real database stays on the device. Benefits: changing a local table never needs a server migration, and the conflict rules live in one place. **Rules** (SQL `sync_incoming_wins`, identical to `src/core/sync/merge.ts`, checked by a test that runs both): last write wins by the writer's HLC, with its time part capped at the moment the server received it (a phone with a clock in the future can't win forever); `xp_events` are append-only, keyed by their idempotency key (the same award from two devices is stored once); a completed quest instance always beats one the rollover marked `missed` (a late-arriving completion turns a missed day active); a `days` row is decided by `low_energy_set_at` (the rest of a day is recomputed on each device). **Security**: Row Level Security lets a user read only their own rows; no direct writes — only `push_records()` (max 500 per call) and `reset_my_cloud_data()`, both using the signed-in user's id; anonymous users can do nothing. Photos, `meta` and `pending_actions` never sync. The migration is tested for real in Postgres (PGlite, in the normal test run) with a stand-in for Supabase's auth schema.

To make that work, **switching low energy off now also records when** (`low_energy_set_at` is the time of the last choice, on or off). Records written by a newer app version are skipped until the app is updated. Bookkeeping (account, pull position, push mark) lives in `meta`, which never syncs. After a restart, the clock is moved past the last pushed HLC so a phone whose clock went back can't write "older" changes that never get pushed.

- **Sync tests and two sync bugs fixed** (task 7.8): the four SPEC 11 sync tests pass (same quest on two devices → one XP event; XP on both devices the same day → same total with the soft cap as one device; a completion arriving after the day closed → the missed day becomes active; focus minutes + typed minutes add up).
